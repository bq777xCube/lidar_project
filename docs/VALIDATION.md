# Как проверить поставку

[К началу](../README.md)

## 1. Проверка файлов без ROS и Docker

Из корня репозитория:

```bash
python3 validation/check_repository.py
```

Скрипт проверяет наличие обязательных файлов, SHA256 исполняемых исходников, Python/XML/JSON-синтаксис, локальные ссылки Markdown и отделение исходников от презентационных материалов. Это проверка поставки, не оценка точности алгоритма. Ни сеть, ни большие эталоны ей не нужны.

## 2. Локальные тесты контракта и ядра

Требуются Python 3 и NumPy. При необходимости используйте отдельное виртуальное окружение:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install numpy
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -v
```

Первичная установка NumPy требует доступного пакета. Обычный запуск тестов сеть не использует. В собранном Docker-образе NumPy уже установлен:

```bash
docker run --rm --platform linux/amd64 --network none \
  -e NEAPY_USE_INSTALLED=1 -e PYTHONDONTWRITEBYTECODE=1 \
  -v "$PWD/tests:/checks/tests:ro" \
  lidar-near:v5-query-first-ru \
  python3 -m unittest discover -s /checks/tests -v
```

Проверяются конфигурация, 16/26-байтный вход, перестановка полей, порядок байтов, заполнение строк, отказы на повреждённой схеме, резервные ветви и простые детерминированные случаи ядра. Это небольшие программные fixtures, не физические препятствия и не повтор полной экспериментальной оценки. При подготовке пакета прошли 20 локальных тестов; [среда и результат](../validation/receipts/local_smoke.json).

## 3. Проверка на bag

Следуйте [инструкции запуска](DEPLOYMENT.md). Короткая демонстрация сохраняет фактически принятые сообщения и логи. Проверка выполняется на исходном bag только для чтения.

## 4. Полный регрессионный комплект

Полная автономная проверка использует отдельно поставляемый `lct26_task5_validation_ru.tar.gz`. В данном Git-архиве нет его больших облаков, эталонов и вложенных зависимостей. Сохранённые `validation/validate_ru.sh` и `validation/tools/` показывают процедуру, но одних этих файлов недостаточно для полного прогона.

Распакуйте **полный комплект** в отдельный каталог, а не поверх этого репозитория. Он должен содержать `validation/archives/`, `validation/solution/` и инструменты. С уже собранным или загруженным образом:

```bash
mkdir -p full_validation
cd full_validation
tar -xzf /absolute/path/to/lct26_task5_validation_ru.tar.gz
bash validation/validate_ru.sh "$PWD/ru_validation_run"
```

Процедура проверяет контрольные суммы вложенных архивов, установленный пакет, численную эквивалентность, основные регрессии, дальние свидетельства и причинный E10-сценарий через DDS. Скрипт завершится с ошибкой при отсутствии обязательных данных; фиктивный PASS не создаётся.

Ожидаемый SHA256 полного комплекта из исходной поставки:

```text
fc193956e69f9c8b41aa07b4190d7ffa7a0262d98c2475ffe95eafdbcae913a9
```

Историческое подтверждение выполненного прогона находится в [receipts/qualification.json](../validation/receipts/qualification.json). Оно относится к ранее проверенной поставке, а не обозначает автоматический повтор полного тестирования при переупаковке файлов.

## 5. Целостность

`validation/source_integrity.json` содержит SHA256 перенесённых исполняемых файлов. Корневой `SHA256SUMS` перечисляет файлы самого репозитория. На Linux:

```bash
sha256sum -c SHA256SUMS
```

На macOS:

```bash
shasum -a 256 -c SHA256SUMS
```

Запуск в целевой среде и нативные измерения i7-9700E остаются отдельной процедурой, а не следствием совпадения хешей.
